# 小说查重（NovelDedup）

本地离线、按**内容**判重的中文小说库清理工具。  
不依赖文件名、不依赖书名作者，纯本地运行，不联网、不上传任何文字。

> 给上万本小说找出"同一部作品的不同副本"，告诉你它们差在哪，  
> 并指出"从第 3 章第 2 段起，连续 4,820 字完全相同"。

---

## 一、它能做什么

| 能力 | 说明 |
| --- | --- |
| 按内容判重 | 不看书名、不看文件名，只比正文 |
| 抗格式差异 | 编码（GBK/UTF-8/UTF-16）、缩进、全角半角、换行、标点，全部归一化掉 |
| 抗插入广告 | 每 1000 字插一条广告照样判为同一本（实测） |
| 抗缺章/合订 | 单卷 vs 三卷合订、完整版 vs 断更版，判为「一方是另一方的子集」 |
| 跨编码判重 | 同一本书一个 GBK 一个 UTF-8，文件体积差 44%，照样判出来 |
| 跨格式判重 | 同一本书的 txt / html / epub / docx 会被判为同一本（实测 5 个文件进同一组） |
| 给证据 | 章节级证据段（起止章 + 原文并排高亮），不是只给一个相似度小数 |
| 给建议 | 组内建议保留哪一本，并说明理由（章节最全 / 内容最多 / 格式更好 / 广告最少） |
| 增量扫描 | 书库没变时 0.1 秒出结果；加几十本书只算新增的那些 |
| 清理 | 一键清理"内容完全相同"的副本 + 手动勾选删除，**一律进系统回收站，可还原** |

### 支持的格式

| 格式 | 支持 | 依赖 |
| --- | --- | --- |
| `.txt` | ✅ 完整（GBK / GB18030 / UTF-8 / UTF-8-BOM / UTF-16，含自动探测） | 无 |
| `.html` `.htm` `.xhtml` | ✅ 去标签、按块级标签断行、处理 `<meta charset>` | 无 |
| `.epub` | ✅ 按 OPF 的 spine 顺序读（不是按文件名顺序） | 无 |
| `.docx` | ✅ 读 `word/document.xml`，段落转换行 | 无 |
| `.pdf` | ⚠️ 仅带文本层的；扫描版要 OCR，本工具不做 | 可选 `pypdf` |

> 扩展名错了也能认（`.txt` 里其实是 HTML、`.docx` 其实是改名的 `.doc`）。
> **认不出或缺少依赖的文件会被明确标出来**，不会静默当成"没有重复"。

**明确不做**：扫描版 PDF 的 OCR、带 DRM 文件、语义级查重（同人文/改写文/译本）、
MOBI/AZW3、UMD/CHM、压缩包内的小说。

## 二、快速开始

### 方式一：双击（推荐）

双击 **`小说查重.pyw`** → 直接打开界面（不弹黑框）。

界面分三层，和漫画查重同一套交互：

```
[分组列表(可过滤)] [组成员(勾选) / 书对 / 匹配段] [A 原文 | B 原文]
```

选目录 → 「开始扫描」→ 左边点一组 → 中间看成员与书对 → 点某个匹配段 →
右边并排显示两本书的原文，并高亮"从哪一段开始对得上"。

双击 `运行工具.bat` 也可以，它会自动挑一个带图形库的 Python。

### 方式二：命令行

```bat
:: 1) 先自检，确认环境正常（不依赖任何真实语料）
python novel_dedup.py --selftest
python novel_dedup.py --verify

:: 2) 扫描书库
python novel_dedup.py --scan "D:\小说" --csv "重复清单.csv"

:: 3) 需要证据明细时导出 JSON
python novel_dedup.py --scan "D:\小说" --json "result.json"
```

| 参数 | 说明 |
| --- | --- |
| `--preset 极速/快速/标准/精细/极精细` | 指纹档位。默认按书库实际字数自动选 |
| `--threads N` | 进程数（默认 8 或 CPU 核数） |
| `--min-bytes N` | 忽略小于 N 字节的文件（默认 1024） |
| `--no-ad-filter` | 不剔除站点广告行 |
| `--no-evidence` | 不算证据段（更快） |
| `--budget-mb N` | 索引体积预算（默认 600 MB），超过自动升档 |
| `--full` | 强制全量重算，忽略历史关系表 |
| `--t2s` | 繁简视为同一本（需要 `opencc`） |

> 命令行**只读**：`--scan` 只出报告，不删任何文件。删除只存在于图形界面。

### 怎么清理

```
[⚡ 一键清理「内容完全相同」]  [全库预勾选（只勾不删）]  [勾选本组多余项]  [清空勾选]  [🗑 删除勾选]
```

- **一键清理**只处理「归一化全文 hash 完全一致」的副本——一个字都不差，每个哈希簇留 1 本。
  这是唯一不经人工判断的删除；广告/缺章/修订版**不会**被它碰到。
- 其余重复由你在**组成员列表**里点 ☐ 逐个勾选；「全库预勾选」可以先把每组多余的勾上再复核。
- 任何删除都要过**二次确认弹窗**（列全清单 + 打勾才能提交），文件**进系统回收站**，随时可还原。
- 每次删除写审计记录：`%LOCALAPPDATA%\NovelDedup\deleted.jsonl`。

### 删完之后还要收尾的两件事

**🧹 清理空文件夹** —— 删掉重复文件后，很多子文件夹会变空。点这个按钮：

- 级联处理（删掉最里层后，外层变空的也一起删）
- 忽略 `Thumbs.db` / `desktop.ini`，这些垃圾文件一并清掉
- **绝不删书库根目录**；空目录是**直接删除**——里面没有任何文件，不需要回收站
  （也正因为如此，网络盘/网络盘上才快：走系统回收站每个目录要 6 秒，直删 0.07 秒）
- 命令行：`python novel_dedup.py --scan D://小说 --clean-empty-dirs`（只列清单，加 `--yes` 才删）

**🗑 清除缓存** —— 清理完、暂时不打算再扫时，可以回收缓存占用的空间：

- 弹窗里选「只清本库」或「清全部书库」，都会显示能回收多少 MB
- **只删缓存，不动你的书**
- 代价：下次扫描要重新计算（1.7 万本约 40 分钟）
- 命令行：`python novel_dedup.py --scan D://小说 --clear-cache --yes`

### 导入上次的结果（不重扫）

工具栏 **「打开结果…」** → 选一个之前导出的 `result.json` → 直接回到那次的结果：
分组、成员、书对、证据段都在，可以继续浏览、筛选、导出、删除。

用途很实际：**一个 1.7 万本的库扫一遍 40 分钟**，改判据、换角度看结果不该再等一遍。

导出 JSON 时会问一句「是否包含全部候选对（含被拒绝的）」：

| 选择 | 文件大小 | 导入后能做什么 |
| --- | --- | --- |
| 只导重复对 | 小 | 重新分组（只能删边，不能补边） |
| **含全部候选对** | 大 | **按新判据重判 + 重新分组**，等价于重扫 |

命令行同样支持：

```bat
python novel_dedup.py --scan D://小说 --json 结果.json --with-candidates
python novel_dedup.py --import 结果.json --csv 重新分组.csv
```

### 指纹缓存在哪儿（用户最常问）

| 数据 | 位置 | 会写进导出文件吗 |
| --- | --- | --- |
| 书籍元信息（字数/章节/编码/大小） | 导出 JSON 的 `books_all` | ✅ |
| 关系指标（Jaccard/包含度/覆盖率/链长） | 导出 JSON 的 `pairs` + `candidates` | ✅ |
| **指纹数组**（每本一个 uint32 排序表） | `%LOCALAPPDATA%\NovelDedup\cache\<库哈希>\fp\*.bin` | ❌ 不写 |
| 原文 | 你自己的书库 | —（按需读取） |

指纹**是存了的**，存在本机缓存目录里，体积约为原文字数的 1.7%
（19 亿字对应约 150 MB）。它只服务一件事：**同机重扫时不必重算**（实测 0.1 秒）。
不塞进导出文件是因为每次导出都会多出几百 MB，而离线重判并不需要指纹——
需要的是每对书的指标，那已经在 JSON 里了。

界面底部 **「指纹缓存位置」** 可直接打开那个目录。换机器想复用缓存，
把整个 `cache` 目录拷过去（书库路径要保持一致）。

### 合订-分卷会单独画结构图

一部书拆成上/中/下卷、另有一个合订全集时，这组不是"互为副本"，而是"整体 ← 分卷"。
界面会画出 **全集在上、分卷在下** 的结构，并标注每个分卷对全集的覆盖率，
再给两条互斥的建议：

1. 保留全集（省空间，但没有分卷目录）
2. 保留分卷（便于阅读，若覆盖不足 100% 可能少一点内容）

## 三、它能保证什么

> **标准档（w=150）：任意两本书只要存在连续 161 个归一化汉字完全相同，  
> 无论它出现在两本书的什么位置，都必定被检出。**

这不是经验值，是 winnowing（Schleimer et al., SIGMOD 2003）的可证明性质：  
任意长度 ≥ `t = w + k − 1` 的公共子串，必定产生至少一个共同指纹。

| 档位 | w | 保证连续 N 字必检出 | 索引体积 |
| --- | --- | --- | --- |
| 极速 | 300 | 311 字 | 0.25 MB / 千万字 |
| 快速 | 200 | 211 字 | 0.38 MB / 千万字 |
| **标准（默认）** | **150** | **161 字** | **0.51 MB / 千万字** |
| 精细 | 100 | 111 字 | 0.76 MB / 千万字 |
| 极精细 | 40 | 51 字 | 1.86 MB / 千万字 |

索引体积约等于**原文字数的 1.7%**——永远比书库本身小两个量级。

## 四、输出怎么读

每组会给一个**关系标签**：

| 标签 | 含义 |
| --- | --- |
| `同一版本` | 归一化后完全相同（只是编码/格式/排版不同） |
| `同一版本（仅插入广告/换排版）` | 正文一字不差，只是多了广告行或换了排版 |
| `同一版本（有细微字符差异）` | 正文基本一致，有零散字符不同（录入错字、少量用词差异） |
| `A ⊂ B（A 缺章）` | A 是 B 的一部分（A 缺章、A 是单卷而 B 是合订本） |
| `B ⊂ A（B 缺章）` | 对称 |
| `章节顺序不同` | 内容基本相同，但章节顺序被打乱 |
| `疑似修订版` / `疑似改字版` | 存在系统性改写，差异较大，需人工确认 |

**判重复的硬底线**（v1.0.1 修正）：

- 整体相似度 `Jaccard < 0.25` → **一律判「无关系」**，不看顺序、不看包含。
  顺序乱不影响 Jaccard，所以"只是乱序"必然 jac 很高；jac 很低只能是"根本不相关"。
- 包含关系还要满足 `共享指纹 / 较大一方 ≥ 2%`。这条专治"短篇 vs 长篇"：
  4,250 字的短篇被 352 万字的长篇包含时，前者只占 0.12%，不构成"同一本书的缺章版"。
- 单个重复组最多 60 本。正常作品不会有 60 个副本；超限说明是**文集/合集文件**
  把一批无关的书连起来了，程序会拒绝合并而不是给你一个 3,216 本的大组。

配套指标（CSV 里都有）：

- **Jaccard**：整体相似度
- **字符覆盖率**：匹配段覆盖了多少正文。**插入广告时会掉 Jaccard，但不掉覆盖率**
  ——这就是"同一版本（仅插入）"和"疑似修订版"的区分依据
- **链长**：最长递增匹配链。共享一堆套话会得到很短的值，沿文本顺序连续对得上会很长

## 五、关于"字数"的口径

同一批书，三种口径能差 20%：

| 口径 | 含义 | 本工具显示位置 |
| --- | --- | --- |
| 汉字数 | 只数汉字 | 状态栏"汉字 X 万" |
| 含标点字符数 | 汉字+标点+数字，**= 起点/阅文的"总字数"** | 状态栏"含标点 Y 万"、CSV「字符A」 |
| 归一化字数 | 汉字+数字+字母，去标点空白 | 判重算法内部使用 |

实测 21 本：汉字 7,896 万 / 含标点 9,049 万。与起点官方字数对照偏差 −0.1% ~ +0.3%
（口径对照方法与平台官方字数一致，偏差在 1% 以内。）

## 六、性能（按字数算，与多少本无关）

| 指标 | 实测 |
| --- | --- |
| 端到端（解码 + 归一化 + 指纹） | **84.9 万字/秒 / 核** |
| 近一亿字（少量真书）首次全扫 | 16 秒（6 进程，含证据） |
| 同一书库无变化重扫 | **0.1 秒**（直接复用关系表） |
| 增量扫描（测例库首扫 0.89s → 加 2 本后 0.16s） | 只算新增的那些，不重算全体 |
| 内存 | 单本约 65 MB；少量真书峰值 186 MB |

增量扫描靠持久化的**关系表**（`edges` 表）：上一轮判出的重复对直接复用，
只对"含新增/变更书"的书对重新精算。这条路径有严格的一致性测试——
`tools/incremental_smoketest.py` 会验证**增量结果与全量重扫逐对一致**。

## 七、已知取舍（如实记录）

1. **短文本**：归一化后不足 2,000 字的文件会被标「短文本：仅 N 字，判定可能不稳」。
   它照常参与判重，只是判据的统计基础弱，界面上会提示。
2. **章节标题写法差异**（`第1章` vs `第一章`）会让每章开头约 12 个 k-gram 不同，
   影响局限在标题附近，不影响正文判定。
3. **广告行删除是保守规则**：整行 + 少于 30 字 + 命中关键词才删。宁可漏删，不误删正文。
   可用 `--no-ad-filter` 关掉。
4. **密集错字的版本**（每几十字一个错字）会落到"疑似修订版"，这是标签变保守，不会漏判。
5. **PDF 只支持带文本层的**，且中文 PDF 的提取质量取决于生成方式；
   提不出文字时会明确标"没有文本层（扫描版 PDF）"。
6. **不做语义查重**：同人文、改写文、译本不会被判为重复。这是有意的。
7. **繁简默认视为不同的书**。需要合并时打开 `繁简视为同一本`（`--t2s`），
   这会改变归一化规则，缓存会全部失效重算。
8. **"一方占另一方不到 25%"不算重复**（jac 底线）。所以：
   - 1000 章的全本 vs 前 10 章试读版 → 不判重（它是试读，不是缺章版）
   - 合集文件 vs 里面某一篇 → 不判重（合集不是"同一本书的副本"）
   这是有意的：这两种情况按"重复"处理会制造海量误判。
9. **文集/合集会单独提示**，不会被并进重复组；但它的成员（各篇）之间如果确实
   是同一篇的不同版本，仍会正确成组。

## 八、隐私与许可证

- **零网络请求**：主程序不导入 `requests` / `urllib.request` / `socket` / `http.client`
  （只用 `urllib.parse.unquote` 解 epub 里的 URL 编码文件名，它不发起任何连接）。
- **删除只进回收站**：不调用 `os.remove`，走系统回收站接口，随时可还原。
- 本项目 **MIT**。

**许可证红线**（电子书生态是 copyleft 重灾区，以下库一律不用）：

| 禁用 | 许可证 | 替代 |
| --- | --- | --- |
| `EbookLib` | AGPL-3.0 | 标准库 `zipfile` + `xml`（自己实现，约 150 行） |
| `mobi` | GPL-3.0 | 不支持 MOBI |
| `PyMuPDF` | AGPL-3.0 | `pypdf`（BSD-3，可选） |

可选依赖：`pypdf`（BSD-3）、`opencc-python-reimplemented`（Apache-2.0）、
`PyInstaller`（GPL with exception，仅打包时用）。缺失时对应功能降级，核心功能不受影响。
